## 二、重点数据生命周期展开

### 2.1 连接密码（与 PL-01 一体）

```text
产生：表单保存 conn_upsert
  ├─ 密码非空 → set_connection_password（钥匙串写入）
  └─ 密码为空 → delete_connection_password（歧义：新建无密码 vs 编辑未重输，PF-01）
使用：load_all() L51-53 读入内存 → 序列化时被 skip_serializing 跳过 → 前端不可见
      执行链路（query/meta/backup）使用前端回传对象 → 密码恒空 → 钥匙串密码零消费
清理：conn_delete / upsert 空密码
孤儿：connections.json 解析失败时 unwrap_or_default 返回空列表（L34-35），
      后续 upsert 的 save_all 将只含新连接 → 旧连接的钥匙串条目永久残留，无清理机制（DS-09）
```

### 2.2 SQL 历史

```text
执行 SQL → saveToHistory：去重置顶 → 超 100 截断
  ├─ persistHistory=false → 仅内存 + 提示「仅保留当前会话」
  ├─ 命中敏感词正则 → 不落盘 + 提示（注意：仅拦截「本条」，此前已持久化的同条不受影响）
  └─ 否则写 localStorage
清空：手动「清空历史」或关闭开关（立即 removeItem）
缺失：无 TTL、无按连接隔离（全局单列表）、无导出
```

## 三、问题清单

### DS-01 密码「存而不取」与读取时机错配【B·PL-01 数据视角】
- 当前设计：钥匙串是密码唯一持久化位置（正确）；但唯一的读取点 `load_all`（connections.rs L52）服务于「读入内存后被序列化跳过」这一无意义用途；真正需要密码的执行链路不读。
- 问题：数据流断链——存储层设计（钥匙串）与使用层设计（前端回传全量连接对象）从未对齐；且每次 conn_list/upsert/delete 都把全部连接密码批量读入内存，扩大了明文暴露窗口（与 PM-04 呼应）。
- 影响：核心功能断裂（PL-01）+ 密钥访问面过大双重问题。
- 建议方向：密码读取收敛到「执行前按 id 单条获取」；conn_list 不再填充内存密码。

### DS-02 空密码语义歧义导致钥匙串误删【B·P4 PF-01 交叉】
- 当前设计：`upsert` 中「密码为空 → 删除钥匙串条目」（connections.rs L76-77）；而编辑表单密码恒空（conn_list 不回传）→ 编辑保存即清密码。
- 问题：空值承载两种含义（「无密码连接」vs「保持原密码」）且取了破坏性的一种。
- 影响：P4 已定级 B（V1「留空保持原密码」）；本报告补充：仅改 upsert 语义不够，需与 DS-01 的服务端解析一并落地，否则「保持的原密码」仍无人消费。
- 建议方向：维持 P4 B1 方向 + PL-01 契约修正。

### DS-03 历史敏感过滤仅覆盖关键词，数据字面量不设防【C·新】
- 当前设计：七类正则（password/secret/token/api_key/access_key/private_key/credential，SqlEditor L33-41）拦截落盘。
- 问题：真实业务 SQL 常以字面量携带个人信息（`UPDATE user SET phone='138****' WHERE id=1`），不含关键词即落盘明文 localStorage；「敏感」的定义停留在口令类，未扩展到数据类。
- 影响：开启本地历史后，测试/生产数据片段长期明文驻留 WebView 存储。
- 建议方向：用户决策敏感策略档位（仅口令类/含 DML 字面量一律不落盘/自定义）；或对持久化历史做提示强化。属产品边界决策。

### DS-04 connections.json 无迁移/备份能力，且明文含内网拓扑【C·新】
- 当前设计：明文 JSON（主机+端口+用户+默认库）；无导出/导入；密码在钥匙串导致「拷文件也迁不走完整连接」。
- 问题：换机/团队共享场景需逐条手工重建（含钥匙串密码）；文件本身泄露内网拓扑与账号名。
- 影响：运维画像（多环境管理）效率受限；安全性为低风险（本地文件惯例）。
- 建议方向：连接配置导入导出（密码可选随行）纳入范围决策；加密暂不必要。

### DS-05 SQL 历史跨连接混存【B·新】
- 当前设计：历史条目仅 `{sql, timestamp, date}`（SqlEditor L98-102），无 connectionId 维度；localStorage 全局单键。
- 问题：切换连接后历史仍全部可见可回填（编辑器 SQL 本身也残留，P4 FL-03 交叉），A 库的 UPDATE 语句可在 B 库连接下从历史一键回填执行。
- 影响：跨环境误执行风险（如把测试库语句跑到生产连接）；历史的有用性也下降（无法按连接检索）。
- 建议方向：历史条目增加连接维度（id+名称），按当前连接过滤展示，全部历史入口可选；与 FL-03 的警示条方案互补。

### DS-06 无日志/诊断数据【C·PL-06 同源】
- 当前设计：全部错误 console.error；无日志文件、无崩溃记录、无慢查询记录。
- 问题：运维画像排障诉求（README/PRD 用户类型表）无数据支撑；用户报障时无可提供物。
- 建议方向：范围决策——最小方案为可选的本地运行日志（连接失败/查询错误/导出结果），默认关闭。

### DS-07 查询结果仅内存不落盘【D·正面】
- 当前设计：结果集仅在内存（maxRows=1000 截断），导出是唯一出仓路径且由用户主动触发。
- 问题：无。隐私友好，边界清晰。建议方向：不动（V1 延续）。

### DS-08 备份文件含全量明文数据【D·观察】
- 当前设计：db_export 生成明文 .sql（含数据，每表上限 10000 行）；导入/执行同步的确认文案均建议「先备份」。
- 问题：属数据库客户端常规形态；确认文案已有风险提示；加密备份属新功能范围。
- 建议方向：不动；若未来做备份加密另立范围决策。

### DS-09 钥匙串孤儿条目无清理【C·新】
- 当前设计：connections.json 解析失败时静默返回空列表（connections.rs L34-35 `unwrap_or_default`）；后续任何 upsert 的 save_all 会用新列表覆盖文件；旧连接的钥匙串密码残留且无引用。
- 问题：json 损坏（手改/磁盘问题）一次即产生永久孤儿；无任何检测/清理界面或命令。
- 影响：低频但不可自愈；钥匙串垃圾累积。
- 建议方向：load_all 解析失败时显式报错而非静默清空（与 UF-07 静默失败治理同向）；可提供「孤儿清理」维护项或文档指引。

## 四、小结

数据分类框架总体正确：密码进钥匙串、历史默认会话、结果仅内存三处设计克制（正面基线）。核心缺陷是**密码数据流断链（DS-01/02，与 PL-01 同根）**——存储决策正确但使用侧从未接通，并派生钥匙串误删与孤儿两个生命周期规则问题。用户数据侧的历史跨连接混存（DS-05）是误执行风险最高的项。共 9 项（B3、C4、D2）。
